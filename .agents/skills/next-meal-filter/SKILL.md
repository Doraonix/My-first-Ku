# 选菜筛选检查

让筛选条件、推荐结果与提示保持一致，并确认用户可以清空条件后重新选菜。

## 使用前确认

- 遵循项目的 AGENTS.md、当前任务及用户已确认的步骤。本 Skill 不代替用户授权，不自动越过“进入下一板块”或提交确认。
- 下文路径均相对项目根目录。先读取 AGENTS.md、PRD.md 第 4 节，并查看工作区改动；按需查看 index.html、app.js、recommendations.mjs 和相关测试，保留已有改动。
- 使用 data/recipes.json 中已审核的菜品。不得为了让测试通过而修改正式菜品、放宽推荐规则或新增后端功能。
- 如果当前任务只是创建或审阅本 Skill，不执行下面的筛选实现与测试，也不把文件读取或格式校验算成筛选任务已完成。

## 必须保持的筛选规则

- 至少勾选一种主要食材才能推荐；只选调料不算有效选材。这与“条件有效但无匹配菜品”是两种不同状态。
- 候选菜至少使用一种已选主要食材，最多缺两种主要食材，且符合难度。简单、普通精确匹配，不限接受两档。
- 缺料按不同主要食材名称计数。调料缺项单独提示，不影响候选资格或排序；先按缺主要食材种数排序，相同时简单优先。
- 修改筛选条件时清除旧推荐及旧详情，提示重新点击“看看能做什么”，不能让旧结果冒充新结果。

## 已确认的一键清空行为

- 提供“清空筛选”按钮；取消全部主要食材与调料勾选，制作难度恢复“不限”。
- 清除推荐列表、当前菜品详情及最近一次有效选材记录；回到初始的待选择提示，不直接展示全部菜品。
- 推荐提示恢复为“请至少选择一种主要食材，再点击‘看看能做什么’。”所表达的含义；详情恢复为请从推荐或收藏中选择菜品的提示。
- 保留收藏及其本地存储，不删除菜品、不清除其他网站数据。清空后从收藏打开详情时，不沿用旧选材判断缺料。
- 连续清空结果一致；再次选择食材并推荐仍正常。资料未成功加载时，清空操作不能将页面伪装成已经可用。

## 实际调用与验证

1. 明确说明正在使用 next-meal-filter，完整读取本文件，说明本次任务范围。只在当前步骤已获授权时实现或修复筛选；只读检查请求不得变成代码修改。
2. 对照上述约定检查现状，实施已获确认的最小改动，补充必要的交互测试。不要仅为增加文件或改动量重写已正确的功能。
3. 用已审核的菜品执行下列三种情况。条件变化后需点击“看看能做什么”才生成新推荐；核对实际菜名、数量、缺料和提示，而非只检查按钮存在。

| 情况 | 条件与操作 | 预期结果 |
| --- | --- | --- |
| 有结果 | 只选番茄，调料不选，难度不限，发起推荐。 | 依次显示番茄炒蛋、番茄鸡蛋炖豆腐；分别缺鸡蛋，以及北豆腐和鸡蛋。缺调料单独提示。 |
| 无结果 | 只选土豆，调料不选，难度普通，发起推荐。 | 没有推荐卡片，明确提示当前条件没有符合的菜，并建议调整食材或难度；无旧结果或旧详情残留。 |
| 清空恢复 | 选番茄、盐、普通，推荐并打开详情，再点击“清空筛选”；重复清空，之后重做“有结果”情况。 | 食材与调料全不选，难度不限，结果和详情恢复待选择状态；收藏不变。重复清空无异常，重选后仍得到两道预期菜品。 |

4. 核对 package.json 后运行项目现有测试与构建命令（当前为 npm test、npm run build），记录真实输出。自动测试应覆盖按钮事件后的状态变化与收藏保留，不能只测试筛选函数。失败时按项目规则报告并等待修复许可，不循环重试。
5. 将浏览器操作与截图交给用户，给出上表对应的短操作步骤。用户亲眼核对前，把页面验证标为待人工确认；模拟页面测试和构建通过不能冒充浏览器验证。截图需保留地址栏、筛选条件和结果。
